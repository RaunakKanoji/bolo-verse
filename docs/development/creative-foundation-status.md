# Initial connected creative studio

This milestone implements the final execution instruction in the [cross-platform master](../product/CROSS_PLATFORM_IMPLEMENTATION_SPEC.md): audit the repository, extend the foundation and deliver the initial web creative studio. It does not implement all 18 screens. The [baseline audit](cross-platform-audit.md) records the starting state; the [implementation plan](../superpowers/plans/2026-11-12-cross-platform-creative-foundation.md) records scope and acceptance.

## Delivered behavior

The existing pearl/lavender Shape Studio canvas now has real image model/aspect controls, explicit private reference upload, durable job submission, server history, status polling, cancellation, confirmed retry, result selection and a download of the actual generated bytes. `/create` and `/studio/image` are compatible entry points; open an authorized project to enable private operations. Local editing, variants, explicit prompt draft saves and edited PNG export remain available. Local imports are sent to storage only through the separate reference-upload action.

Each project/session owns its client store and Query client. Account switching and verified access denial dispose private prompts, history, requests and image URLs. A denied project remains gated until a new scope is opened. HTTP test fixtures live in a separate browser harness; there is no production auth bypass.

Image uploads use actor-owned ten-minute reservations, signed bounded staging PUTs and server-selected immutable final keys. Finalization rechecks project edit rights, MIME, byte size, SHA-256, encoded structure and full codec decoding before publishing a ready asset. PNG/JPEG/WebP input is bounded to 20 MiB, 8192 pixels per dimension and 16,777,216 total pixels; decoding consumes/discards at most 64 MiB RGBA. Generation references are capped at 10 MiB to leave room for inline base64/prompt overhead. Authorized project editors may reference ready images shared within that project; generation prompts/history remain private to the author.

The existing processing job table now supports image generation. The separate request table retains prompt/model/aspect/reference/provenance privately. Submission keys are scoped to actor and project; reuse with changed input conflicts. Limits are ten new generation requests/hour and twenty upload reservations/minute per actor. Duplicate submission does not consume another job or generation budget. A SQL lease claims a queued job once; a persisted dispatch marker prevents repeating a provider call. Ready output metadata, asset linkage and final job state publish in one authorized transaction.

Cancellation stops publication; it cannot promise the provider stopped billing. Membership is checked before dispatch and after private awaits. Ambiguous failures and expired processing leases become failed jobs; they never silently repeat a possibly billed request. Retry is an explicit new request and charge warning. The worker uses one fixed Gemini endpoint, an explicitly configured supported model, no automatic network retry, bounded responses and sanitized failures. It accepts one non-thought decodable image; it never fetches caller-selected provider URLs or remote references.

## Boundaries and operations

`apps/web` remains the sole backend, `apps/spatial-web` remains the canonical R3F editor, and `apps/visionos` remains independent SwiftUI/RealityKit. Canonical scene v1, A-Frame, the mono recorder and existing native behavior are preserved. The original `/api/v1/capabilities` contract remains compatible; image creation has an additive capability endpoint. Native receives generated models/routes, not a new native image-generation screen.

## Configuration and recovery

Set Clerk, Neon and private R2 configuration from `.env.example`, plus `GEMINI_API_KEY` and the separate `GEMINI_IMAGE_MODEL`. The allowed models are `gemini-3.1-flash-image`, `gemini-3-pro-image` and `gemini-2.5-flash-image`. Credentials alone do not establish live verification or account model access. Missing configuration disables generation while retaining local editing.

The POST handler schedules its persisted job with Next `after`. Configure a hosting duration that accommodates the bounded provider request; this route declares 180 seconds, and the provider timeout is 120 seconds. A reliable deployment must also schedule `pnpm jobs:run` regularly to recover queued work after process loss. It processes at most five jobs sequentially and marks expired processing leases interrupted. The script prints counts, not prompts, keys or signed URLs. A provider failure still consumes the actor request budget; this is an abuse limit, not a billing ledger.

R2 stays private. Bucket CORS must allow the exact application origin, PUT and the `Content-Type`/`If-None-Match` headers; browsers derive the signed Content-Length from the File body. Basic signed headers avoid dependence on optional checksum APIs. The server retains SHA-256 byte verification and uses supported Content-MD5 for final writes. Confirm actual CORS, conditional-write behavior and provider acceptance with the intended live accounts before rollout.

`pnpm jobs:cleanup` is a read-only candidate count by default. `pnpm jobs:cleanup --apply` deletes at most twenty eligible objects. Schedule applied cleanup separately with server-only credentials. It cleans expired staging copies, expired unpublished upload-final objects, and failed/cancelled generated-output orphans after 24 hours. Keys must match exact server UUID paths. Unpublished upload assets/reservations are retired atomically before deletion; every deletion rechecks state and protects published/other asset references. Deletion markers prevent already-cleaned rows from starving subsequent batches. Failures retry safely on a later run. A bucket lifecycle for `staging/images/` is useful defense in depth; do not apply a blanket lifecycle to published `private/images/` or `private/generated/` prefixes.

Gemini adapter implementation follows the primary [GenerateContent API reference](https://ai.google.dev/api/generate-content) and [image generation guide](https://ai.google.dev/gemini-api/docs/generate-content/image-generation). Storage operations follow [R2 conditional operations](https://developers.cloudflare.com/r2/api/s3/conditional-operations/), [presigned URLs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/) and [S3 compatibility](https://developers.cloudflare.com/r2/api/s3/api/). Recheck model availability before enabling an account. Video/audio/3D generation and full delivery/review workflows remain later phases.

## Acceptance limits

Automated tests use real local PostgreSQL semantics and local codec decoding, with fixture provider/storage responses and browser HTTP fixtures. No live Clerk/Neon/R2/Gemini/Sarvam calls, billed requests, cloud deletions, live migrations, deployment or physical headset verification were performed. Full-codec decoding is not a malware scan. Asset provenance records the request and immutable bytes; it does not claim a provider billing receipt or a complete content-version/review workflow. Native accessibility and live/device gates from the existing validation document remain open.

Final verification passed: `pnpm check` (14 tasks, 523 tests in 54 files, both production builds), all 50 Chromium cases (production routes plus isolated HTTP component fixtures), 17 Swift bidirectional fixtures and nine invalid payloads, 48 Swift core tests, and unsigned generic visionOS Simulator compilation. Frozen offline install and whitespace checks passed. Independent review findings were corrected and rechecked. See the [progress tracker](../../context/progress-tracker.md) for integration history.
